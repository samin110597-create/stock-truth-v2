# Q-State Standalone Quant Terminal

The quant terminal is a **separate application** deployed at `/quant/`.

It does not reuse the classic Stock Truth HTML, CSS, provider router, technical-analysis engine, structure engine, reversal engine, or setup engine. The only shared runtime resources are:

- sanitized market-data snapshots under `data/`
- the bundled TradingView Lightweight Charts library
- repository build/deployment infrastructure

## Credential architecture

API credentials remain GitHub Actions repository secrets only. The standalone quant page never asks for, stores, embeds, or receives an API key.

Add secrets at **Repository Settings → Secrets and variables → Actions**. Supported names include:

- `MASSIVE_KEY` or existing `POLYGON_KEY`
- `FMP_KEY` / `FMP_API_KEY`
- `FINNHUB_KEY` / `FINNHUB_API_KEY`
- `ALPHA_VANTAGE_KEY` / `ALPHAVANTAGE_KEY`
- `FRED_KEY` / `FRED_API_KEY`
- `SEC_USER_AGENT`

GitHub Actions can use these keys to create sanitized snapshots. Credentials are never written into those snapshots.

## Standalone analysis engine

The quant engine under `quant/src/` independently implements:

- confirmed pivot structure
- BOS and CHoCH
- liquidity-sweep detection
- RSI pivot divergence
- EMA trend state
- velocity, acceleration and jerk
- curvature
- Shannon entropy
- Hurst persistence estimate
- DFT-style dominant-cycle detection
- realized and Parkinson volatility
- ATR compression
- volume anomaly and absorption proxies
- regime classification
- deterministic Monte Carlo scenario paths
- retrospective directional context with Wilson intervals
- action state, preferred entry zone, breakout/breakdown trigger, fixed invalidation, and targets

The browser chart also draws forward median and distribution-band projection paths for 20 bars.

## Data behavior

For U.S. stocks and ETFs, the standalone app first looks for sanitized repository snapshots. If a suitable snapshot is unavailable, it has its own independent public chart fallback. It does not call the classic terminal's provider code.

For futures and commodities, it reads sanitized futures snapshots generated by GitHub Actions. The prepared commodity universe includes GC, SI, CL, NG, HG, PL, PA, ZC, ZW and ZS.

## Integrity rules

- The classic `web/index.html` must not link to or depend on the quant app.
- `/quant/` must not import classic analysis/provider modules.
- The old `web/quant` and `src/quant` implementations must not ship.
- Browser credential storage and API-key query construction are deployment failures.
- Model conviction is an evidence score, not a probability.
- Projections are scenario estimates, not guaranteed future prices.


## Secured provider routing

Production GitHub Actions now prefers Massive/Polygon aggregate bars when an entitled market-data secret is available, then falls back to the independent public chart source rather than silently mixing providers. The generated bar payload records the provider that actually supplied each timeframe.

The Q-State page also reads a sanitized `data/quant/context.json` manifest generated server-side. It uses:
- Finnhub: throttled SPY quote cross-check.
- FMP: throttled SPY quote cross-check.
- Alpha Vantage: throttled SPY quote cross-check.
- FRED: daily 10Y nominal yield, 10Y real yield, 10Y breakeven inflation and trade-weighted USD context.

Those cross-source and macro observations are shown in the interface as context/health. They do not silently change the trading score until a factor model is separately validated.

Production pushes, manual runs and scheduled runs now execute the secured collectors; pull requests never receive repository secrets.


## Q-State 2.0 calibration layer

GitHub Actions now trains a separate directional model for 15M, 1H, 4H and 1D at 5-, 10- and 20-bar horizons from sanitized stock/futures snapshots.

Features are causal and include:
- 1/5/20-bar log returns
- EMA20/50/200 distance
- RSI state
- ATR percentage and compression
- volume Z-score
- 20-bar range position / breakout state
- state-filtered latent velocity and acceleration
- realized volatility
- trend/regime interactions

Validation is expanding chronological walk-forward with an embargo between train and test windows. Calibration curves and conditional return bands are built from out-of-sample predictions only.

A probability is promoted to the UI only when all of these are true:
- at least 3 walk-forward folds
- at least 500 out-of-sample observations
- Brier skill versus the historical base-rate forecast is at least 0.5%
- log loss is no worse than the base-rate forecast
- at least 60% of walk-forward folds have positive Brier skill without worse log loss
- median fold Brier skill is positive

If those gates fail, probability is shown as **WITHHELD**. The deterministic setup engine can still produce a rule-based WATCH/DEVELOPING/READY state, but it may not present an unvalidated percentage as predictive probability.

Execution uses a pre-specified primary horizon rather than choosing the best historical result after the fact: 15M→20 bars, 1H→10 bars, 4H→5 bars, 1D→10 bars. A probability is shown only if that pre-specified horizon passes promotion. Projected 5/10/20-bar paths use validated OOS conditional return bands for any horizon that passed; non-promoted horizons remain explicit regime/volatility simulation fallbacks.

Multi-timeframe EMA20/50 bias is used as an execution gate, not silently mixed into calibrated probability. Macro/API context remains descriptive until synchronized historical factor data is available for separate validation.
